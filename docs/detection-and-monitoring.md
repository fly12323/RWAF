# 弱口令检测与运行监控

## 业务流量检测

web1 新增“弱口令检测”页面。所有站点共用一份配置，可编辑或导入 UTF-8 原始字典，并选择预计算形式：明文、无盐 MD5、SHA-1、SHA-256、标准 Base64、无填充 Base64URL。MD5/SHA 十六进制忽略大小写；明文和 Base64 区分大小写。不同形式产生相同字符串时，事件使用配置顺序中第一个命中的表示名称，不代表能够推断业务采用的算法。

内置字典有 40 个常见示例，属于启动字典，不是完整弱口令库。字典最多 10000 项，每项最多 256 字节。修改后重新预计算集合，请求中不解码、不计算密码哈希、不执行字典枚举。字典版本由字典及表示方式生成，可在事件里追踪。

认证接口按 Host（可为空）、方法、路径识别；路径支持精确匹配或末尾 `*` 前缀匹配，第一条命中规则生效。配置最多 100 条，方法支持 POST、PUT、PATCH。每条规则包含登录/注册/改密类型、JSON/表单/按 Content-Type 识别格式，以及最多 8 个密码字段。JSON 的 `data.password` 表示嵌套字段；表单字段名精确匹配。默认提供 `/login`、`/register`、`/password` 示例，需要按实际业务接口调整。

请求路径只做接口筛选，并在已有请求体读取后，把匹配请求体复制到有界内存队列。两个异步 worker 提取指定字段并做整个字段值的集合查询，不扫描其他正文、响应和文件。最多检测 64 KiB 请求体，队列容量 256；超限、格式不支持、解析失败或字段缺失计入 `skipped`，队列满计入 `dropped`，均继续转发。配置关闭时不接收新任务，已接收任务仍按接收时的配置处理。

在黑名单、CC 或爬虫阶段被提前拦截的请求不会进入正文读取阶段，不参与弱口令检测；超过 WAF 请求体上限而返回 413 的请求也不投递检测任务。

命中后生成 `weak_password` 事件，通过原 Kafka 日志链路入库。事件只保存请求 ID、站点、客户端 IP、接口、类型、表示名称、字典版本和时间，不保存账号、密码、对应哈希或字典条目。登录结果固定为 `unknown`，不根据 200、429 等响应推测成功。注册/改密事件同样只表示提交了弱密码，不表示业务已接受。

只检测与告警，不阻断业务流量。随机盐、随机加密、组合哈希、客户端自定义协议和 WAF 无法解密的 HTTPS 流量不能按当前固定集合识别。未命中不代表密码安全，检测未完成及丢弃计数需要结合监控查看。

## 日志脱敏和性能边界

已匹配认证接口即使关闭检测，也会在普通请求日志进入 Kafka 之前隐藏整个请求体、响应体及规则匹配数据。Authorization、Cookie、Set-Cookie、含 token/password/api-key 的头字段全局脱敏；Referer、Location 的查询串和片段隐藏。请求日志与爬虫日志不保留原始查询参数。转发内容不修改。

认证请求未配置、请求方法不匹配等情况不属于认证正文脱敏范围，因此应完整配置认证接口；文件上传不做密码识别。历史日志不会被自动清理或重新脱敏。

异步表示转发不等待检测结果，不表示零资源开销。仍有接口匹配、请求体复制和队列投递成本，worker 与代理共享 CPU 和内存；检测内容只在当前 API 进程内存中处理，密码不发送到 Kafka。重启及停机可能丢弃未处理检测任务，退出时尽力清理缓冲区；命中事件若 Kafka 发送队列已满也可能丢弃，计入 `publish_errors`。

配置写入后本进程立即切换，其他应用实例每 5 秒刷新。刷新失败保留最后有效配置并提供监控异常。普通日志、检测事件及其告警共享消费者，部署时先升级消费者，再升级 API；旧消费者不支持新增事件种类，会停止消费。

## 管理后台密码

创建账号、改密、管理员重置密码均由后端统一校验：至少 12 个字符、不超过 bcrypt 的 72 字节，不允许常见弱口令、简单常见词加数字符号、纯数字、连续字符、重复组合、账号名开头或首尾空白。业务检测字典可编辑，但不会放宽管理账号的固定密码策略。

新安装必须在 `.env` 配置强 `ADMIN_PASSWORD`；缺失或不合格时 API 启动失败，不再创建 `admin123`。已有管理员时环境变量不覆盖密码。旧账号密码无法从哈希直接判断，用户下次使用弱密码登录时，成功验密后获得带改密限制的 JWT；只能读取自己的账号、改密或退出。web1 跳转改密页面，服务器独立限制其他 API。成功改密撤销会话，重新登录后解除限制。已经签发的旧会话不会因本次代码升级自动撤销。

## 运行监控与系统内告警

后台默认每 15 秒采样，管理 API 读取已有快照，不在页面刷新时探测依赖。可配置 5–300 秒间隔。监控项包含 PostgreSQL、Redis、Kafka 健康，Kafka 主题尾 offset 与配置消费者组提交 offset 的差值，消费者心跳，日志队列占用、丢弃、发送错误，检测队列丢弃、未完成、投递失败与配置刷新异常，以及代理 RPS、平均延迟、5xx 比例、P99 延迟桶和当前 WAF Go 堆内存/协程数。

消费者每 5 秒向 Redis 更新组级心跳，默认超时 30 秒。心跳存在不保证消费者无积压，需同时看 Kafka lag 和重试状态。多消费者情况下心跳代表该组近期有实例存活；不会逐实例列出所有消费者。请求与内存指标属于当前 API 进程，不是整个 Docker 主机的 CPU/内存。延迟桶采用 1、5、10、25、50、100、250、500、1000、5000 ms 和最后溢出桶标记 60000 ms，P99 是估算值。

当前告警聚合按单 API 部署设计，符合项目现有 Compose 拓扑。扩展到多个 API 副本时需要增加实例标识或监控汇总，避免不同实例互相覆盖运行告警状态。

运行告警按异常类型聚合，持续异常更新次数，恢复后自动关闭；累计丢弃/错误计数按采样增量判断，避免历史错误永久告警。弱口令告警按站点与接口聚合，事件重放不重复计数；可确认并手动标记已处理，后续再次命中会重新打开新告警。确认表示已阅，不代表故障恢复。

数据库故障时运行快照提供实时异常，持久化告警失败标志为 true，并在内存保留待补记异常；数据库恢复后补记并按当前健康状态关闭。补记的创建时间为恢复后的写入时间。数据库故障期间 API 进程同时重启会丢失尚未持久化的运行告警。Redis 故障时管理认证也受影响，需结合外部探活观察 API 可用性。

告警目前只在系统内显示，不发送邮件、消息或 Webhook。关闭运行告警持久化后仍采样，不影响弱口令告警。审计员可查看检测事件、监控快照和告警；管理员/操作员可改配置、确认或处理告警。新操作写入操作日志。

## API

| 方法和路径 | 用途 |
|---|---|
| GET/PUT `/api/v1/weak-password/config` | 全局字典、表示形式和认证接口规则 |
| GET `/api/v1/weak-password/events` | 分页检测事件，支持 site_id、kind 筛选及当前进程计数 |
| GET `/api/v1/monitor/status` | 最近运行快照及实时异常 |
| GET/PUT `/api/v1/monitor/config` | 全局采样和告警阈值 |
| GET `/api/v1/monitor/alerts` | 分页告警，支持 status、source 筛选 |
| POST `/api/v1/monitor/alerts/:id/acknowledge` | 确认已阅 |
| POST `/api/v1/monitor/alerts/:id/resolve` | 手动关闭弱口令告警 |

## 验证

隔离 Compose 项目使用 PostgreSQL 15432、Redis 16379、Kafka 29094，不切换正式部署。完整 HTTP 报告为 `detection-monitor-check/report.json`；故障检查和检测开关性能对比在同目录另存结果。Go 集成测试覆盖 PostgreSQL/Kafka 重放去重、弱口令告警重复计数及旧后台账号受限改密，单元测试覆盖编码匹配、字段精确匹配、Host/路径筛选、表单、错误格式、队列边界、管理密码策略及监控异常恢复。

本机微基准：接口未命中约 48 ns/op、32 B/op；异步 JSON MD5 命中约 1.17 µs/op、856 B/op。微基准不代表实际转发性能或长期系统容量。

最终干净环境的 116 项 HTTP 功能检查全部通过；独立的 7 项真实故障与恢复检查全部通过。PostgreSQL、Redis、Kafka 实际集成测试、`go test ./...`、`go vet ./...` 和 web1 TypeScript/生产构建通过。

32 并发、每场景 4 秒、两轮检测开关对比结果如下，完整数据见 `detection-monitor-check/load.json`：

| 场景 | 检测关闭 RPS（两轮） | 检测开启 RPS（两轮） | 关闭 / 开启 P99（ms） |
|---|---|---|---|
| 普通 GET | 8573 / 6481 | 6390 / 7902 | 11.12 / 14.51；17.72 / 13.10 |
| 登录 JSON POST | 4268 / 3789 | 4043 / 4575 | 24.19 / 25.12；23.23 / 20.04 |

所有请求均返回预期 200，检测队列处理 34524 个任务、丢弃 0、未完成 0、投递失败 0。测试使用强密码请求比较检测成本，未覆盖大量弱口令命中产生告警的持续负载。短时结果波动明显，不能据此断言检测没有开销。

原日志发送队列累计丢弃 59117 条事件，Kafka 消费曾出现积压。`log_dropped` 和 `kafka_lag` 告警均已实际产生并在恢复后关闭。这是高峰日志链路容量不足的证据，转发成功不意味着日志完整；本轮只验证新功能和识别该问题，没有把此性能测试视为稳定容量验收。

故障检查还观察到 Kafka 长时间断连会使现有消费者退出；正式 Compose 的 `restart: unless-stopped` 会负责重启。测试 Compose 不配置自动重启，需显式恢复消费者；运行监控能识别心跳超时。数据库故障期间的未持久化告警补记已通过实际验证。
